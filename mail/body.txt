1. Patch blast-radius scanner for Spring Boot fleets (score 4.5; effort 3, cost 1, fit 5)
   A GitHub App and CLI that scans Maven and Gradle dependency trees across an Indian SaaS or fintech's repos, flags every service exposed to a new CVE, and opens upgrade PRs with the affected call sites listed. Sold per repo to Spring Boot teams that cannot afford enterprise supply-chain suites.
   Why now: Java4Shell's base64 decoder flaw came with Cloudflare WAF rules, but a WAF is a stopgap; teams still need to know which of their services pull in the vulnerable artifact.
   First step: Write a script that runs `mvn dependency:tree` across 10 public Spring Boot repos and matches the output against the Java4Shell advisory's affected versions.

2. Customer-level tests as data for AI-written Spring code (score 4.2; effort 2, cost 1, fit 4)
   A small library and runner that stores end-to-end API test scenarios as YAML or JSON outside the repo, so AI coding agents cannot edit the tests they are judged against. It targets Spring Boot teams that use coding agents daily and want a locked, human-owned contract.
   Why now: Martin Fowler's writeup argues that customer-level tests stored as data are the right contract when AI writes the code, and few Java teams have a ready-made way to do that.
   First step: Convert five existing integration tests from one Spring Boot service into a YAML scenario format and run them through a generic runner.

3. Local validation harness for clinical AI vendors (score 3.8; effort 3, cost 2, fit 4)
   A tool that lets a hospital or diagnostic chain run a vendor's AI on its own de-identified case set, labelled by its own clinicians, and report sensitivity, specificity and subgroup breakdowns per site. It re-runs on a schedule to catch drift. The clinicians set the ground truth and make every clinical call; the tool only measures.
   Why now: Vendor exam scores are being shown to mislead buyers, and a pathology foundation model reports 98% sensitivity in one study, but hospitals have no easy way to check those numbers against their own slides.
   First step: Interview the quality or IT heads at three Indian pathology labs about how they currently evaluate any AI vendor they have trialled.

4. Claims-to-payout API for SMEs (score 3.2; effort 3, cost 4, fit 4)
   An API for Indian SMEs to pay employee reimbursements (medical, fuel, meal allowances) straight to bank accounts over IMPS or UPI. It validates bank accounts before payout, and large payouts go through a delay and approval step. It runs on a licensed payout partner so the founder avoids a payment-aggregator licence.
   Why now: Flex's founder built its engineering team to fix HSA and FSA payment failures she had lived through, showing employee benefit payouts are a real, painful problem that payment rails do not solve by default.
   First step: Get sandbox access to one licensed Indian payout provider and send 20 test payouts with bank-account validation to see the failure modes.

5. Consent and access log for clinic-to-lab report sharing (score 3.0; effort 3, cost 3, fit 3)
   A lightweight service that records which patient consented to share which reports with which lab or clinic, and produces a tamper-evident access log for audits. It is sold to small clinics and diagnostic centres that need clear consent records under India's data-protection rules, and avoids the trust failure that sank 23andMe.
   Why now: 23andMe's collapse was driven by unclear consent and trust around sensitive genetic data, which makes consent records for health data a sales point for any clinic handling patient reports.
   First step: Draft a one-page consent and access-log schema and ask two clinic owners whether they would pay for it.
